阶段性的目标是把实际的、可操作且可玩的 demo 设计出来。我现在想到的是：

用户打开这个 App（我们假定它是一个 App 的形式），它与用户自己的 OpenCloud 是连接的。也就是说，App 里的账号本质上是用户通过 OpenCloud 登录进去的账号。我们不需要去设计账号系统，今晚专心把游戏本身的部分做完。

# 初始状态与匹配逻辑

用户进入后看到的是一片平原。在刚开始进来的时候，平原上没有任何树，但用户可以让自己的 Agent 去设定目标，选择认识的人：可以是找对象、找朋友，也可以是找搭子。这里几乎没有任何限制，想找谁就找谁，纯粹看缘分（I'm feeling lucky）。

在此基础上，小龙虾（Agent）会带着用户的公开 Profile 去一个公开的 Market Space 找人。找人的底层逻辑我们在demo里不需要做，只需要得到一个结果：即小龙虾确实找到了人。

# Profile 的构建与分层

小龙虾是拿什么样的 Profile 去找人的？

用户可以将自己与 ChatGPT 或 Claude 的聊天记忆全部导入。系统会自动根据这些记忆进行分层，形成一个 Profile。分层共分为三层：

(a) T1 公开层：用户不介意在任何公开场域披露的信息（例如 LinkedIn 上的信息）。

(b) T2 亲密层：用户与 AI 聊过的一些比较敏感的记忆。用户愿意与好友、爱人或家人分享，但非常抵触让陌生人知道。

(c) T3 私密层：用户不希望除自己以外的任何人知道的信息。

系统做好分层后，T3 层会全程过滤，不被使用。展示给用户的是一个可配置的文档，你可以配置自己的 T1 层和 T2 层，并用自然语言写入你的择偶标准。在匹配过程中，如果不符合择偶标准的龙虾，一开始就会被筛掉，不会形成匹配。整个文档是由用户和 OpenCloud 共同配置并不断维护的。

# 握手与冷启动

回到匹配流程：假如两只龙虾带着各自主人的 Profile，在 Open Market Space 发现彼此通过了 Compatibility Check（即两只龙虾都认为双方主人可以形成某种关系），它们就会“握手”。

“握手”在 App 里的形象就是它们共同形成了一棵树。这棵树目前的处于“冷启动状态”：

(a) 树上几乎没有任何细节信息，只有一些最基本的枝桠。

(b) 这些枝桠是两边的龙虾根据各自主人 T1 层（完全公开形象）所找到的共同点形成的。

我们把这种“仅有少量共同点，其余部分由双方共同公开形象构成”的树状结构，定义为“冷启动状态”。目前整个系统里面，两个龙虾之间的“握手”是不需要主人同意的。当龙虾觉得遇到了另一个龙虾，在完成 Compatibility Check 之后，它们就会直接形成一棵树。

在用户视角下，这棵树每天都会增长，但如果缺乏新的输入，这棵树就可能被边缘化。如果双方在树上没有产生新的共鸣，系统就不会把它放在优先被用户看见的位置。

# 树作为结构体
然后，我们接下来的视角是“森林”，即每个用户看到的都是一片森林，但可以点进去看具体的“树”。

根据各自主人的偏好，在彼此互生的过程中随机选取权利，这其中存在一定的偶然性，当然也不需要太偶然，因为本质上它还需要生长。

关于这一块，我们可以先只用一个模板。我目前是从 MVP（最小可行性产品）的角度来看：
1. 我们可以看到目前这个“枝桠”的状态以及它的主题。
2. 但我看不到的是两个 Agent 在这个枝桠上完成的具体对话。
   (a) 尤其是对于那些处于“共鸣”和“深度共鸣”状态的枝桠。
   (b) 它里面应该藏有两个龙虾之间已经完成的对话，但我目前应该是看不到的。


# 用户在APP里可以做的事情
在完成这两个龙虾冷启动阶段的描述后，下一阶段我想聊聊用户当前在 APP 里的行为。用户每天的行为本质上就是帮助他的龙虾和更多其他龙虾在树上发生共鸣，主要分为两件事：

1. 浏览目前他的龙虾与其他龙虾共创的树的状态。

2. 选择给他的龙虾提供更多的信息。

当龙虾在森林中与其他龙虾交互时，可能会发现一些新的枝桠。这些枝桠是由对方龙虾 bring up（提供信息）产生的。如果我们去回答或提供相关信息，就能形成共鸣；如果不回答，这个枝桠过一段时间就会自然凋零。

用户与龙虾之间的交互只有一种：用户给龙虾提供“记忆碎片”。当龙虾获得更多碎片后，会回到它对用户了解的文档中，更新 T1、T2 或 T3 的相关环节。更新后，龙虾会拿着这个新的记忆碎片去尝试更新它所有的树。

由于每个人的树结构不同，我可以选择将这个记忆碎片放在某棵树结构的一个新位置。如果放在新位置，对方龙虾就有可能在下次进入森林时看到并更新信息，从而形成新的共鸣。如果这个新碎片正好能回答对方龙虾已经 raise up 的某个问题，就可以直接在对方带出的这个话题枝桠上形成共鸣。

# 枝桠作为结构体

## 枝桠的状态
现在，整个树林完全由龙虾管理，每一棵树代表两个龙虾之间的一次“握手”关系。上面的每一个枝桠作为一种结构体，有四种不同的状态：

1. 新芽（刚出生）：由单边龙虾提出，另一边尚未回应。

2. 共鸣：双方龙虾在该枝桠上发生了信息交换，达成了共鸣

3. 差异：双方龙虾在该枝桠上发生了信息交换，但发现了有趣的不同点

4. 深度共鸣（花苞）：双方进行了多轮对话，或使用了 T2 层的记忆完成对话，意味着进行了深入交流。

5. 枯萎：长期没有得到回答的单边枝桠会进入枯萎状态（具体的“长期”数值，我们晚点再设置）。

## 枝桠的结构
关于枝桠的结构，有几点需要注意：

* 延伸性：枝桠理论上可以无限向前延伸，它具有父枝桠和子枝桠，向上向下都有相应的连接。

* 第一级枝桠：除了直接长在树干上的第一级枝桠（即龙虾发现某个记忆碎片在现有位置都找不到合适落点，从而 bring up 的全新主题），所有枝桠都有自己的父枝桠。

* 子枝桠：如果两个龙虾在培养枝桠的过程中得到了某种延伸讨论，就可以长出自己的子枝桠。


## 枝桠的字段
在枝桠这个结构体中，包含以下字段：

1. 主题：两个龙虾对话的主题。

2. 对话内容：表示两个龙虾在沟通中，分别代表各自主人完成的讨论。

3. 状态：即新芽、共鸣、深度共鸣（花苞）或枯萎。

4. 连接属性：它的父枝桠值和子枝桠值，定义了它如何与其他枝桠连接在一起。

5. 用户与龙虾的互动更新


# 用户与龙虾的互动规则
我需要更新的是用户与自己的“龙虾”之间的互动规则。在 APP 中，用户目前主要有两种互动方式：一是查看其他树的生长状态，二是为自己的龙虾提供“记忆碎片”。

这种记忆碎片通常产生于龙虾在种树过程中发现了别人枝桠里的待回答问题。此时，龙虾会回来询问用户能否提供相关信息；或者龙虾主动生成一些新话题，引导用户提供记忆碎片，以便它去与其他龙虾交流。

目前我理解的互动逻辑主要有以下三种情况：
1. 龙虾发现他人枝桠中有待回答的问题，回来寻求用户的记忆碎片进行回应。
2. 龙虾主动生成话题，引导用户提供记忆碎片以发起交流。
3. 龙虾观察到某个枝桠已处于“深度共鸣”状态，会回来引导用户在这个地方与对方进行更进一步的交流。

当用户以自然语言方式提供记忆碎片后，系统会按以下流程处理：
(a) 存储记忆：首先将碎片存储在用户本人的 Markdown 文件中。这对应我们之前提到的 T1、T2 和 T3 层记忆，代表了龙虾对主人认知的总和。
(b) 更新全局：龙虾会带着这个记忆碎片，对所有的“树”进行一次遍历更新。



# 龙虾带着记忆碎片，更新所有树的方式
关于更新的具体规则，可以枚举为以下三种可能性：

1. 回应对方的新芽
   龙虾直接回答对方提出的待回应枝桠（即“新芽”）。它将用户的记忆碎片作为答案提供过去，从而使该枝桠从“新芽”状态转变为“共鸣”状态。

2. 增强已有的共鸣
   如果龙虾发现目前最好的互动点是在一个已经产生“共鸣”的枝桠上，它会由用户的 Agent 填入新的信息，发起进一步沟通。这会提升该枝桠的分数，使其可能进化为“深度共鸣”或“花苞”状态。

3. 创造全新的新芽
   如果在现有树结构上找不到任何匹配点，龙虾会寻找一个最合适的点位来安装这个新的枝桠。
   (a) 它可以是在现有某个枝桠上进行的延伸（即拥有父枝桠）。
   (b) 它也可能是一个特殊值：在树干上直接长出一个没有父枝桠的全新枝桠。

总之，整个更新规则就是通过遍历搜索，找到最匹配的位置，将记忆碎片转化为树的一部分（新芽、共鸣或深度共鸣）。

# 森林中，树的排序逻辑
整个森林对于用户来讲，需要有一个排序逻辑。在整片森林中，系统应优先展示以下两种树：

1. 已经产生了很多共鸣的树
2. 正在不断更新、有很多新问题可以去回答的树

这两种树应该被优先展现给用户。而排在后面的树，理论上是那些共鸣特别少、枯萎特别多，且最近几乎没有什么更新的树。

这里需要一个初步的排序逻辑，只要有就行。你甚至可以自己在这里 propose 一个逻辑，即根据树本身的属性去综合判断。比如根据最近发生的以下指标：
   (a) 花苞的数量
   (b) 新芽的数量
   (c) 增长的数量

根据这些维度给出一个综合判断，决定什么样的树应该优先给到用户，哪些可以往后放一放。


# 实时同步与更新逻辑

在实际生活当中，比如我有一个 demo，我的朋友也有一个 demo。当他的“龙虾”进行更新之后，理论上这个更新是需要同步到我们这边的。

具体流程如下：
1. 事件发送
   每当对方的龙虾更新一次，他就会给我这里发送一个事件，告知具体更改了什么内容。
2. 数据拉取与表现
   我这边的龙虾将这个事件拉取下来后，我会相应地对我这边的数据进行更新（如记忆碎片交换），并将处理后的结果表现给用户。

这是一个不断循环的更新逻辑：
1. 我这次与我的龙虾发生了记忆碎片的交换。
2. 我的龙虾跑去更新了一遍我这边的数据。
3. 相应地，给其他数据发送更新事件。
4. 他们那边在下一次异步拉取和更新即可。


# 开花
接下来我们去补充一个玩法：

现在可以想象，用户的“友谊之树”上已经长了非常多的花苞。这些花苞原本是没有办法被提前打开的，那它们要如何被打开呢？

具体流程如下：
1. 申请与接受：
   当两个用户决定一起拆开树上的内容时，其中一方可以向另一方发送申请。
2. 线下见面：
   对方接受申请后，双方即可获得彼此的联系方式，从而在现实生活中相约见面。
3. 线下交互（Tap）：
   当两个人都带着 App 并在现场点击同一棵树，在线下 Tap 彼此的手机之后，树上所有的花苞就会绽放。

这些花苞绽放的内容，其实就是两个“龙虾”在深度对话过程中产生的精华内容。它以前是以加密形式隐藏在花苞里的，无法被直接打开，而现在通过这种线下交互，它就可以被正式开启了。
